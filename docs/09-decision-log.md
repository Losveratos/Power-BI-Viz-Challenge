# 09 — Decision log

This file records the analytical and engineering decisions behind the Round 3
entry in the form of architecture decision records (ADRs). Each record has three
parts:

- **Context** — the situation and the constraint that forced a choice.
- **Decision** — what was chosen, stated in one sentence where possible.
- **Consequences** — what follows, including the costs, not only the benefits.

ADRs are numbered from ADR-001 upward and are never renumbered or deleted. A
decision that is later reversed is not edited away: the original record stays,
and the reversal is recorded in the "Superseded or reconsidered" section at the
end with a pointer to the ADR that replaced it. The value of the format is that
it preserves the reasoning available at the time, including reasoning that turned
out to be wrong.

Supporting numbers are quoted from `analysis/out/audit_summary.json`,
`analysis/out/findings.json`, `analysis/out/audit_report.md` and
`analysis/out/robustness.md`, all of which are regenerated by the scripts in
`analysis/`. Requirement IDs such as P-01 refer to the checklist in
`docs/01-challenge-brief.md`.

## ADR-001 — Read the semantic model out of the official starter .pbix

**Context.** The analysis needs the data in a form Python can work with. There
were two routes. The first was to download the underlying TMDB dataset from
Kaggle and work from the CSV. The second was to read the model out of the
starter `.pbix` the competition supplies. These are not equivalent. The Kaggle
dataset is a living upload that gets refreshed; the starter file is a frozen
snapshot taken at some point before the round opened, with its own transformation
steps already applied. Working from the CSV would mean the audit describes a
slightly different set of films from the one every competitor's report is built
on — different row counts, possibly different revenue values, and no way to tell
which discrepancies were ours. R-11 requires that the entry use the provided
dataset, and the strictest reading of that is to use the provided *file*. A
practical point pushed the same way: the Kaggle host was not reachable from the
build environment, so the CSV route was not available even if it had been
preferable.

**Decision.** Extract the model directly from the starter `.pbix` using the
`pbixray` Python library, which parses the VertiPaq `DataModel` stream out of the
file without requiring Power BI Desktop or any Microsoft runtime, and therefore
runs on Linux in CI. `analysis/01_extract_model.py` downloads the starter file,
prints its SHA-256 so the audit is pinned to one identifiable snapshot, writes
the model metadata (schema, relationships, DAX measures, and the M queries) to
`work/model/`, and writes one Parquet file per table to `work/extract/`.

**Consequences.** The audit describes exactly the data every competitor
receives, and the `[budget] > 0` filter in the supplied `Movies` query became
visible as a finding rather than an invisible precondition — it is the subject of
section 2 of `docs/02-data-audit.md`. The extraction is reproducible on any
platform and independent of a Kaggle account or of network access to Kaggle.
The costs: a dependency on `pbixray`, which is a third-party reverse-engineering
of an undocumented format and could break on a future file; and the audit
inherits any error already baked into the starter file, with no upstream version
to compare against. Two large tables, `Keyword` and `Keyword Bridge`, are
skipped at extraction because the report does not use them and they add over 1.2
million rows.

## ADR-002 — Treat budgets below $10,000 as unusable

**Context.** Production budgets in this data are volunteer-entered, and a
frequency count of the Budget column shows values repeating far more often than
any real cost distribution allows. Real budgets are near-continuous: two
unrelated films essentially never cost the same amount to the dollar. Yet 3,531
films report a budget of exactly 100, 3,107 report exactly 1,000, 2,619 report
exactly 500, and 1,731 report exactly 1. Ten values account for more than a
quarter of the starter file. These are form-filling defaults, not measurements.
The danger is specific: budget sits in the denominator of every return figure in
the report, so a placeholder does not merely add noise — it manufactures
spectacular results. A film with a recorded budget of 1 dollar and an ordinary
gross produces a return in the thousands, and the subset's maximum ROI of
4,144x is exactly that phenomenon.

**Decision.** Require Budget >= $10,000 for a film to enter any financial
metric. The threshold is the named constant `MIN_CREDIBLE_BUDGET` in
`analysis/02_data_audit.py`, `03_metric_exploration.py` and `04_robustness.py`.

**Consequences.** 51,634 of the 85,394 starter rows (60.5%) carry a budget below
$10,000 and are excluded from financial analysis; within the funnel as ordered
this step removes 27,879 films, the largest of the five cuts this analysis
applies. The floor is deliberately blunt and will discard some genuine
micro-budget productions along with the defaults — a real $8,000 film is
indistinguishable from a placeholder by value alone. That trade is accepted: a
handful of lost real films costs less than one fabricated 4,000x return in a
report about responsible data use. Note that $10,000 is itself one of the
repeated values (2,165 films), so the floor is inclusive of a cluster that is
partly placeholder; the sensitivity analysis in ADR-003 and check C covers the
effect of moving the revenue and vote floors, and the report states the budget
floor as an explicit assumption rather than a fact.

## ADR-003 — Require at least 50 votes before a rating is used

**Context.** TMDB's Vote Average is a mean of user ratings with no minimum
sample. An 8.0 from three voters and an 8.0 from thirty thousand are stored
identically. 56,028 starter rows have a Vote Average of exactly 0 and 55,958
have a Vote Count of exactly 0, which is the same films appearing as unrated
rather than badly rated. Beyond those, there is a large population with a
handful of votes whose averages are dominated by whoever happened to arrive
first. Since one of the report's two headline relationships is between rating
and return, a rating column full of low-n noise would be a direct threat to the
finding.

**Decision.** Require Vote Count >= 50 before a film's Vote Average is used.
The threshold is the named constant `MIN_VOTES_FOR_RATING`.

**Consequences.** Films whose average rating rests on a handful of voters are
dropped: 75,060 of the 85,394 starter rows have fewer than 50 votes, and within
the funnel the step removes a further 2,486 films to give the final 7,733. The
threshold is arbitrary, so check C in `analysis/out/robustness.md` re-runs the
whole analysis at 0, 10, 50, 100 and 500 votes, crossed with three revenue
floors. Across all fifteen combinations — subsets from 4,614 to 10,439 films —
the Budget–Revenue rank correlation stays between 0.656 and 0.758, Budget–ROI
stays at or below zero (-0.247 to -0.052), and Rating–ROI stays positive (0.265
to 0.340). The conclusions therefore hold from 0 votes to 500. What does move
is the level: median ROI ranges from 1.79x to 2.61x and the break-even share
from 38.7% to 51.8% across the same grid, which is why those two figures are
always reported as properties of the stated subset rather than as facts about
cinema. A secondary cost is a popularity bias: requiring 50 votes preferentially
retains films that found an audience, which compounds the survivorship effect
described in ADR-004 and check A.

## ADR-004 — Treat Revenue = 0 as unknown, not as zero earnings

**Context.** Revenue has no nulls in the starter file: 0 missing values across
85,394 rows. It also has 67,436 rows equal to exactly 0 — 79.0% of the file. A
zero here is not a measurement that a film sold no tickets; in a
volunteer-maintained database it means nobody entered a gross. The two readings
lead to opposite analyses. Read as earnings, those 67,436 films drag the median
revenue of the starter file to zero, make almost every film a catastrophic loss,
and make any return figure meaningless. Read as unknown, they are simply outside
what the data can speak to.

**Decision.** Treat Revenue = 0 as unknown. Operationally, require Revenue >=
$10,000 for a film to enter any revenue, profit, return or break-even
calculation, using the same reasoning about placeholder magnitudes as ADR-002.

**Consequences.** Rows with unknown revenue cannot enter any ratio, so they are
excluded from the analysable subset rather than counted as zeros. This is the
largest data-quality problem in the file: measured on its own against the
starter rows, the revenue floor would exclude 73,941 films (86.6%), second only
to the vote-count threshold's 75,060 (87.9%), and it is the criterion behind the
report's central caveat. Inside the funnel as ordered the step removes 17,974
films, less than the raw figure because the preceding steps have already removed
many of the same rows. The decision has a second-order effect that is more
serious than the row loss and is treated as a finding in its own right: revenue
reporting is not missing at random. Films budgeted above $50M report revenue
91.1% of the time; films budgeted between $10,000 and $100,000 report it 7.8% of
the time. Excluding unknown revenue therefore excludes low-budget failures far
more often than low-budget successes, which is why check A concludes the
low-budget return advantage is largely survivorship and why the report shows the
reporting-rate table next to that claim.

## ADR-005 — Define success as return on production budget against a 2.5x gross break-even multiple

**Context.** The brief states there is no single right answer and asks entrants
to define success clearly (J-01). Four defensible definitions are available in
this data: box-office gross, profit as revenue minus budget, audience acclaim,
and return on budget. They do not agree. The top-100 lists by gross and by
return share zero films, and no film appears in all four top-100 lists. Gross
and profit overlap at 0.91, which is to say profit as defined here is mostly a
restatement of gross. The problem with gross is that it measures size: budget
predicts revenue at rank correlation 0.676, so a ranking by gross is close to a
ranking by how much was spent. The top budget decile earns a median gross of
$300,257,475 against $2,500,000 for the bottom decile, 120 times more, while
returning 2.48x against 4.02x — less. A report built on gross would conclude
that spending more is what makes a film successful, which is nearly a
tautology.

**Decision.** Define success as return on production budget, measured as gross
revenue divided by production budget, and treat a film as breaking even at 2.5x.
The multiple is the named constant `BREAKEVEN_MULTIPLE` in
`analysis/03_metric_exploration.py` and `04_robustness.py`.

**Consequences.** The report measures performance rather than scale, and small
films can appear alongside large ones without being drowned. Against this
definition 41.4% of the 7,733 analysable films break even, 68.6% return more
than their budget in gross, and the median return is 1.96x.

The 2.5x multiple is an **assumption imported from industry practice, not a
figure derived from this data**, and the report labels it as such wherever it
appears. The reasoning is that exhibitors retain roughly half of ticket revenue
and that marketing and distribution spend is not included in the reported
production budget, so a film needs a gross well above its budget before it
returns anything. Both of those are domain knowledge; neither is measurable
here. Two consequences follow. First, the break-even share is only as good as
the assumption, so the report presents it as "breaks even under a 2.5x
assumption" rather than as "was profitable", and never labels an individual film
profitable or unprofitable. Second, because the multiple is a constant applied
uniformly, it does not distort comparisons between groups even if the level is
wrong: a different multiple would move every break-even share up or down
together and leave the ranking intact. The definition also inherits ADR-002's
denominator problem, which the $10,000 floor addresses, and it says nothing
about ancillary revenue, which the data does not contain.

## ADR-006 — Do not inflation-adjust

**Context.** The subset spans release years 1915 to 2023. The median budget of
a pre-1980 film is $2,489,500 and of a 2015-or-later film $19,000,000; the
corresponding median revenues are $10,000,000 and $28,000,000. Most of that
difference is the value of money, not the scale of filmmaking. The standard
remedy is to deflate every figure by a price index. A CPI or GDP-deflator series
is an external dataset, and Round 3 prohibits adding external datasets, joining
to outside sources, and using any information that would materially change or
enrich the underlying data (P-01, P-02, P-05). There is no price information
anywhere in the provided files, so there is no compliant way to construct one
internally.

**Decision.** Report nominal dollars only, and never compare dollar amounts
across eras. Use ratios for any cross-era comparison.

**Consequences.** The report contains no inflation-adjusted figure and makes no
claim that requires one. Dollar amounts are compared only within an era, and
every chart that could be misread as a cross-era money trend is either scoped to
one era or converted to a ratio. Ratios are legitimate across eras because
inflation largely cancels in a revenue/budget quotient: numerator and
denominator are denominated in the same year's dollars. Return and break-even
share are therefore the only quantities the report tracks over the full span,
and check E in `analysis/out/robustness.md` publishes the era table with a
verdict that says plainly never to compare its money columns. The cost is real:
the report cannot say whether films have genuinely become more expensive in real
terms, which is a question a viewer will reasonably have. It says so rather than
answering it with an unauthorised index. A second caution rides along with the
era table: pre-1980 covers only 780 films, and per check A the ones that survive
are those somebody thought worth recording decades later, so its 4.03x median
return is treated as thinly sampled and selection-affected.

## ADR-007 — Report medians, never means, for money

**Context.** Every money quantity in this data is severely right-skewed. Mean
revenue in the analysable subset is $84,932,088 against a median of
$25,155,355 — the mean sits above roughly three quarters of the films it claims
to summarise. The top 1% of films take 14.2% of all revenue. The distortion is
worse for ratios: mean return is 6.26x against a median of 1.96x, with a maximum
of 4,144x. A single film with a recorded budget just above the $10,000 floor and
a substantial gross can move the average of thousands of rows.

**Decision.** Every money figure and every ratio in the report is a median.
Means appear only alongside their medians, as evidence for why the median was
chosen.

**Consequences.** Reported figures describe a typical film in the group rather
than an arithmetic artefact, and group comparisons are not hostage to whichever
group happens to contain a blockbuster. The report gains a specific piece of
content from the decision: the mean-versus-median gap is itself shown on the
methodology page, because "the average film returns 6.26x" is the kind of
plausible, quotable, wrong number a responsible report should demonstrate rather
than merely avoid. The costs are that medians do not sum or decompose — a median
of medians is not a median, so aggregates are always recomputed from rows — and
that the median deliberately hides the tail, which is why distributions are
shown wherever a page has room and why the top-1% revenue concentration is
stated explicitly. Counts of films above and below a threshold are used in place
of totals where a total would be misleading.

## ADR-008 — Use Spearman rank correlation rather than Pearson

**Context.** The report needs to state how strongly budget, runtime, rating,
vote count and popularity relate to each success definition. Pearson's
correlation measures linear association on raw values and assumes roughly
symmetric distributions with comparable variance. None of these variables
qualifies: revenue, budget and return are all heavily right-skewed, and return
has a maximum of 4,144x. On raw values a handful of blockbusters and a handful
of extreme ratios would determine the coefficient, and the resulting number
would describe those few films rather than the relationship.

**Decision.** Use Spearman rank correlation throughout, computed as Pearson on
the ranks of each variable. The `spearman()` helper in
`analysis/03_metric_exploration.py` does this, and `04_robustness.py` uses the
same rank method in the threshold grid.

**Consequences.** The coefficients describe monotone association — does a film
that ranks higher on one variable tend to rank higher on the other — which is
what the report actually claims, and they are robust to the skew and to the
placeholder-driven extremes that survive the $10,000 floor. This is what makes
the central contrast reportable: budget ranks with revenue at 0.676 but with
return at -0.105, so money buys gross and not performance. Vote count ranks with
revenue at 0.698, higher than budget does, and with return at 0.386. The costs
are that rank correlation cannot be interpreted as a proportion of variance
explained, so the report does not present r-squared-style statements; that it
detects only monotone relationships, which is why the budget-to-return
relationship is also shown as deciles, where the non-monotone U-shape that a
single coefficient of -0.105 conceals becomes visible; and that no correlation
of either kind establishes direction, which ADR-005's companion caveats and
check B address separately.

## ADR-009 — Show every breakdown with its film count, and mark small groups as unreliable rather than hiding them

**Context.** Breakdowns by genre, production company, release month and era have
wildly uneven group sizes. Genres range from 3,521 films for Drama to 4 films for
TV Movie. Sorted by median return, the top of the genre table is TV Movie at
4.84x on 4 films and Documentary at 4.04x on 66 films — both well ahead of any
well-populated genre. Presented without counts, that ranking is a misleading
comparison of exactly the kind J-14 penalises. There are two usual responses:
silently drop small groups, or show everything and let the viewer sort it out.
Dropping is itself a hidden analytical choice, and it removes the viewer's
ability to see that the analysis had a boundary.

**Decision.** Every breakdown in the report carries its film count, and groups
below 100 films are marked as unreliable rather than removed. The
`genre_performance()` function sets an explicit `Reliable` flag at
`Films >= 100`. Production companies use a separate, higher floor of 25 films for
inclusion in the studio table, because company-level medians are the noisiest
breakdown in the analysis.

**Consequences.** A viewer can always see how much data is behind a bar, and the
unreliable groups remain visible as data rather than vanishing. TV Movie (4
films) and Documentary (66 films) appear in the genre table flagged, and no
narrative claim rests on them; the genre statements in the report are made on
groups such as Horror (948 films, 2.26x), Animation (447, 2.44x) and Drama
(3,521, 1.71x). Era breakdowns carry counts for the same reason, which is what
lets the pre-1980 row (780 films) be read with appropriate caution. The costs
are chart clutter — counts have to be fitted into labels, tooltips or a secondary
axis on every breakdown visual — and the risk that a viewer reads a flagged
number without reading the flag, which is mitigated by ordering and annotation
rather than by removal.

## ADR-010 — Commit no raw data to the repository

**Context.** The analysis needs the starter `.pbix` and the extracted Parquet
tables on disk. Committing them would make the repository self-contained, which
is convenient. Two considerations weigh against it. The underlying dataset is
redistributed under the Open Data Commons Attribution License (ODC-By 1.0),
whose attribution obligations attach to redistribution; committing a derived
copy of the data into an MIT-licensed repository would put two licences over the
same tree and invite confusion about which covers what. Separately, the data is
large — the starter file plus the extracted tables run to hundreds of megabytes
before the skipped keyword tables are even considered — and binary blobs of that
size in git history are permanent.

**Decision.** Commit the scripts and the aggregated outputs; commit no raw data.
`work/` is listed in `.gitignore`, so `work/starter.pbix`, `work/extract/*.parquet`
and `work/model/*` never enter the repository. The generated aggregates in
`analysis/out/` — the Markdown reports, the JSON findings and the CSV tables —
are committed, because they are small, they are the evidence the report's claims
rest on, and they are aggregate rather than a redistribution of the dataset.

**Consequences.** The repository stays small and single-licensed, and the data's
own licence terms are not entangled with the code's. Anyone can reproduce the
whole analysis by running `analysis/01_extract_model.py`, which fetches the
official starter file and prints its SHA-256 so the reproduction can be checked
against the snapshot this audit describes. The cost is that the repository is
not self-contained: reproduction requires network access to the starter file's
host, and if that URL ever moves, the fingerprint in the extraction step is the
only remaining evidence of which snapshot was used. Committing the aggregates
alongside the scripts is what keeps the audit auditable in the meantime — a
reader can compare a regenerated `audit_report.md` against the committed one and
see immediately whether anything has drifted.

## ADR-011 — Ship a bundled-data build alongside the canonical Kaggle pipeline

**Context.** The canonical semantic model loads the raw Kaggle CSV, exactly as
the official contest instructions describe ("replace the file path in the
Source step"). The person producing the final .pbix has no Kaggle account, and
the build environment cannot reach Kaggle either, so the canonical pipeline
cannot be refreshed anywhere in this workflow.

**Decision.** `05_build_semantic_model.py --bundled` emits a second build of the
same model whose Power Query loads per-table CSVs shipped next to the .pbip.
`08_export_bundled_data.py` produces those CSVs by exporting every table of the
official starter .pbix's own model — the exact snapshot every competitor
receives — with no values added, dropped or altered. The two builds share the
derived-column pipeline, all 24 measures, all calculated tables and all
relationships verbatim; only the loading steps and the single path parameter
(`CsvPath` vs `DataFolder`) differ. CSV types are re-applied under a pinned
en-US culture so the ISO dates and dot decimals parse identically on any
machine locale.

**Consequences.** A machine without Kaggle access can refresh and produce the
submission .pbix. The provenance chain lengthens by one documented,
reproducible step (starter .pbix → parquet → CSV) and is disclosed here and in
the build guide. The canonical build remains in `src/pbip` unchanged and stays
byte-identical across regenerations; the bundled build lives under `work/` and
is never committed, because ADR-010 keeps raw data out of the repository.

## Superseded or reconsidered

Nothing has been superseded or reversed so far.

This section exists so that a reversal has somewhere to go. If a decision above
is changed, the original ADR stays exactly as written — including its reasoning,
including the parts that turned out to be wrong — and an entry is added here
naming the superseded ADR, the ADR that replaces it, and what new evidence forced
the change. Decisions are not quietly rewritten to look as though they were
always correct, because the point of the log is to show how the analysis was
reasoned about, not to present it as having arrived fully formed.
